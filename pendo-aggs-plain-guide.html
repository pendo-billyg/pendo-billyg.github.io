Pendo Aggregations — Plain-English Guide

Aggregations are how Pendo pulls and reshapes your product data. This guide explains what each piece does in plain language so you can read and understand an aggregation without writing code.

External POST https://app.pendo.io/api/v1/aggregation auth: X-Pendo-Integration-Key header
Internal POST https://app.pendo.io/api/aggregation/s/:subID?all=true auth: session cookie — no auth header (:subID = subscription ID)

What is an aggregation?

An aggregation is like a recipe: an ordered list of steps. You start with a pile of data, and each step changes it a little — keep some rows, bucket them, add up numbers — until you're left with the answer. Each step hands its result to the next, like an assembly line. It's written in JSON (a structured text format), but you mostly just read it top to bottom.

sourceget data→ filterkeep rows→ groupbucket→ sortorder→ limittake top
Two everyday comparisons: building an aggregation is a lot like building a pivot table in a spreadsheet (start with raw data, filter it, group it, total it up). And it's the same machinery that powers what you already see in the Pendo app — the charts, the Data Explorer, segment counts, retention. The app just builds these recipes for you behind the scenes.

Anatomy of a request

Every request wraps a pipeline — the ordered list of steps. The first step is always a source (what data to start from), usually with a timeSeries (which dates to cover).

What it looks like

{
  "request": {
    "requestId": "active-visitors",
    "pipeline": [
      {
        "source": {
          "events": null
        },
        "timeSeries": {
          "period": "dayRange",
          "first": "now()",
          "count": -30
        }
      },
      {
        "identified": "visitorId"
      },
      {
        "group": {
          "group": [
            "visitorId"
          ],
          "fields": [
            {
              "minutes": {
                "sum": "numMinutes"
              }
            }
          ]
        }
      },
      {
        "sort": [
          "-minutes"
        ]
      },
      {
        "limit": 10
      }
    ]
  }
}

In plain words: start from activity data for the last 30 days, drop anonymous visitors, add up each visitor's active minutes, sort highest first, and keep the top 10. That's the whole recipe.

PieceWhat it means
pipelineThe list of steps, run top to bottom.
sourceWhat you start with (see below). Always the first step.
timeSeriesThe date range for event data. first is a start time, count is how many days/hours (a negative number counts backwards from the start).
a rowOne record in the pile — one visitor, or one day's activity, or one event. Steps add, remove, and reshape rows; you get a list of rows back at the end.
requestIdJust a name/label for the query.

Where the data comes from

The source is the pile of data you start from. Picking the right one is half the battle. Think of these like the different objects and reports you already know in Pendo.

Users & things

SourceWhat it gives you
visitorsOne row per visitor, with their current metadata. Includes anonymous visitors unless you filter them out.
accountsOne row per account.
pages / featuresOne row per tagged Page (a screen) / Feature (a clickable element).
guidesOne row per guide (in-app message).

Activity over time (already summed up)

SourceWhat it gives you
eventsOverall activity, pre-totalled per visitor per day into numEvents (clicks/views) and numMinutes (time). Best for trends.
pageEvents / featureEventsSame idea, but for a specific Page / Feature.
guideEvents / pollEventsEach time someone saw/advanced/dismissed a guide, or answered a poll.

Every single action (big & detailed)

SourceWhat it gives you
singleEventsOne row for every individual action a visitor takes. Powerful but heavy — always use a short date range and a limit.
rawEventsThe most raw, unprocessed form. For debugging only — prefer singleEvents, and don't suggest this to customers.
The key distinction: events is like a summary tab — the daily totals are already worked out for you, so it's fast and great for "how much activity over time." singleEvents is like the raw log — every single click, useful when you need event-by-event detail, but big and slow. Even then, singleEvents isn't the rawest form: it's been lightly cleaned up and made readable, while rawEvents is the completely unprocessed firehose — messier, slower, and debugging-only. So from most to least processed: events (daily totals) → singleEvents (every event, tidied) → rawEvents (every event, untouched). Reach for the summary first, and the raw log only when you truly need each event.

The steps (operators)

Each step is written as { "stepName": ... }. Here are the everyday ones, in plain language.

filter

keeps only matching rows

Looks at every row and throws away the ones that don't meet a condition.

Example

{
  "filter": "numMinutes > 5 && country == \"US\""
}
SpreadsheetThe Filter button — show only rows where time > 5 and country is US.
In PendoThe rules you add when building a segment.

identified

drops anonymous visitors

Keeps only known (logged-in / identified) visitors and removes anonymous ones.

Example

{
  "identified": "visitorId"
}
SpreadsheetFiltering out the blank / "anonymous" names so you're left with real people.
In PendoThe "identified visitors only" choice you see on many reports.

group

buckets rows, then summarizes each bucket

Puts rows into buckets by a field (e.g. one bucket per visitor), then works out a summary number for each bucket.

Example

{
  "group": {
    "group": [
      "visitorId"
    ],
    "fields": [
      {
        "minutes": {
          "sum": "numMinutes"
        }
      }
    ]
  }
}
SpreadsheetA pivot table: rows = visitor, value = sum of minutes.
In PendoAny metric "broken down by" visitor, account, page, etc.

reduce

squashes everything into one summary row

Collapses all the rows into a single summary — one grand total.

Example

{
  "reduce": {
    "totalEvents": {
      "sum": "numEvents"
    },
    "uniqueVisitors": {
      "count": "visitorId"
    }
  }
}
SpreadsheetThe grand-total row at the bottom of the sheet.
In PendoThe single big number on a dashboard tile.

select

keeps only certain columns

Trims each row down to just the fields you list (and lets you rename them). Everything else is dropped.

Example

{
  "select": {
    "id": "visitorId",
    "mins": "numMinutes"
  }
}
SpreadsheetHiding or deleting the columns you don't care about.
TipLeave select out entirely to keep every column.

eval

adds a calculated column

Adds a new field worked out from existing ones, keeping everything else.

Example

{
  "eval": {
    "minutesPerEvent": "numMinutes / numEvents"
  }
}
SpreadsheetA formula column, e.g. =minutes/events.

switch

labels rows into buckets by range

Sorts a number into named buckets. (Note: a row that fits no bucket is dropped.)

Example

{
  "switch": {
    "tier": {
      "minutes": [
        {
          "value": "low",
          "<": 10
        },
        {
          "value": "mid",
          ">=": 10,
          "<": 60
        },
        {
          "value": "power",
          ">=": 60
        }
      ]
    }
  }
}
SpreadsheetA nested IF that labels each row Low / Mid / Power.

sort

orders the rows

Orders rows by a field. A minus sign in front (-minutes) means highest-first.

Example

{
  "sort": [
    "-minutes"
  ]
}
SpreadsheetSort Z→A (largest first) or A→Z.

limit

keeps the first n rows

Keeps only the first n rows and drops the rest. Great for "top 10" and for testing (limit to 1 just to see the shape of the data).

Example

{
  "limit": 10
}
SpreadsheetKeeping just the top 10 rows after sorting.

More steps (you'll see these less often)

These show up in more complex aggregations. You usually just need to recognise what they're doing when reading one.

StepWhat it does, in plain words
countCounts how many rows there are. Like the row count at the bottom of a spreadsheet.
setAdds a column with the same fixed value in every row.
segmentKeeps only the people who belong to a saved segment.
bulkExpandAttaches a visitor's (or account's) profile info onto each row — like a VLOOKUP that pulls in extra columns about that person.
joinMerges rows that share a key into one combined row.
forkRuns two different summaries on the same data at once, then combines the results.
spawnPulls from two different sources and combines them into one stream (often paired with join).
unwindTakes a list inside one row and splits it into one row per item.
unmarshalOpens up data that's packed into a single text field so you can read the pieces. Mostly used with rawEvents.
useragentTurns a browser's "user agent" string into readable parts: browser name, version, operating system.
catDoes nothing — passes rows straight through. You'll almost never need it.

Ways to summarize

When you bucket rows (group) or total everything (reduce), these decide how the numbers get summarized — exactly like the value calculations in a pivot table.

SummaryWhat it does
count (no field)How many rows are in the bucket.
count (with a field)How many unique values — e.g. count of distinct visitors.
sumAdds the numbers up.
avgThe average.
min / maxThe smallest / largest value.
firstThe first value seen (sort first if order matters).
listCollects the values into a list.
concatJoins the values together.
countIfCounts only the rows that meet a condition.
Pivot-table parallel: these are the "Summarize values by" choices — Sum, Count, Average, Min, Max. Same idea, same results.

Mini-formulas

Inside steps like filter and eval you can write little formulas. They work just like spreadsheet formulas. Comparisons use == (equals), != (not equal), > < >= <=, and you combine conditions with && (and) / || (or).

FormulaWhat it doesSpreadsheet equivalent
if(test, a, b)Gives a if the test is true, otherwise b. Leave off b and it's blank when false.IF()
isNull(x)True if the field is empty / missing.ISBLANK()
contains(text, "abc")True if the text contains "abc".SEARCH() / Contains filter
startsWith(text, "abc")True if the text starts with "abc".LEFT() check
len(x)How long a piece of text (or a list) is.LEN()
round / floor / ceil(x)Rounds a number.ROUND()
now()The current time (used to say "the last 30 days").NOW()
formatTime(fmt, t)Turns a timestamp into a readable date.TEXT() on a date

Worked examples

Three real recipes, read as plain steps.

1 · Most active visitors, last 30 days (top 10)

The recipe

{
  "request": {
    "pipeline": [
      {
        "source": {
          "events": null
        },
        "timeSeries": {
          "period": "dayRange",
          "first": "now()",
          "count": -30
        }
      },
      {
        "identified": "visitorId"
      },
      {
        "group": {
          "group": [
            "visitorId"
          ],
          "fields": [
            {
              "minutes": {
                "sum": "numMinutes"
              }
            }
          ]
        }
      },
      {
        "sort": [
          "-minutes"
        ]
      },
      {
        "limit": 10
      }
    ]
  }
}

Reads as: take the last 30 days of activity → drop anonymous visitors → add up each visitor's minutes → sort most-active first → keep the top 10.

2 · Total events & how many people

The recipe

{
  "request": {
    "pipeline": [
      {
        "source": {
          "events": null
        },
        "timeSeries": {
          "period": "dayRange",
          "first": 1404745200000,
          "count": 30
        }
      },
      {
        "reduce": {
          "totalEvents": {
            "sum": "numEvents"
          },
          "uniqueVisitors": {
            "count": "visitorId"
          }
        }
      }
    ]
  }
}

Reads as: take 30 days of activity → squash it all into one row with two numbers: total events, and the count of distinct visitors.

The recipe

    "pipeline": [
      {
        "source": {
          "events": null
        },
        "timeSeries": {
          "period": "dayRange",
          "first": 1404745200000,
          "count": 30
        }
      },
      {
        "group": {
          "group": [
            "visitorId"
          ],
          "fields": [
            {
              "minutes": {
                "sum": "numMinutes"
              }
            }
          ]
        }
      },
      {
        "switch": {
          "tier": {
            "minutes": [
              {
                "value": "low",
                "<": 10
              },
              {
                "value": "mid",
                ">=": 10,
                "<": 60
              },
              {
                "value": "power",
                ">=": 60
              }

Reads as: total each visitor's minutes → label them Low / Mid / Power by how many minutes → then count how many visitors fall in each label. (Two pivot tables, one feeding the next.)

Good to know

The order of steps matters. The recipe runs top to bottom — each step works on whatever the step above handed it. Filtering early keeps things fast.
Pick the right activity source. events is the pre-summed daily total (a summary tab) — fast, best for trends. singleEvents is every single action (a raw log) — use only when you need event-level detail, with a short date range. rawEvents is debugging-only.
"Count" can mean two things. count with no field = how many rows; count with a field name = how many unique values of that field.
Dates are required for activity data, and they're in milliseconds. Event sources need a timeSeries; the times are milliseconds since 1970 (you'll usually use now() instead of typing one). People/things sources like visitors don't need dates.
Leave out select to keep all columns. Only add select when you want to trim down to specific fields.
