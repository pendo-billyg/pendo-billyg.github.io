Pendo Aggregations → SQL

A cheat sheet for translating Pendo's JSON aggregation pipeline into the SQL you already know. Left column is Pendo agg, right column is the SQL equivalent.

External POST https://app.pendo.io/api/v1/aggregation auth: X-Pendo-Integration-Key header
Internal POST https://app.pendo.io/api/aggregation/s/:subID?all=true auth: session cookie — no auth header (:subID = subscription ID)

The mental model

A Pendo aggregation is a pipeline: an ordered list of steps. Each step takes rows in and emits zero or more rows out — the output of one step is the input to the next. That's the key difference from SQL: instead of one declarative statement the optimizer reorders, you write the stages yourself, top to bottom, like a chain of CTEs.

source→ filter→ group→ eval→ sort→ limit ≈ FROM → WHERE → GROUP BY → SELECT → ORDER BY → LIMIT
Big idea: SQL is declarative (say what you want, engine picks the order). Pendo aggs are imperative (you list the steps in execution order). The vocabulary maps almost 1:1 — you're mostly just re-sequencing what you already know.

Query anatomy

Every request wraps a pipeline array. The first step is always a source (your FROM), optionally scoped in time by timeSeries (your date WHERE).

timeSeries now uses now() / -30

Pendo aggregation

{
  "response": { "mimeType": "application/json" },
  "request": {
    "requestId": "active-visitors",
    "pipeline": [
      { "source": { "events": null },
        "timeSeries": {
          "period": "dayRange",
          "first": "now()",
          "count": -30
        } },
      { "identified": "visitorId" },
      { "group": {
          "group": ["visitorId"],
          "fields": [ { "minutes": { "sum": "numMinutes" } } ]
      } },
      { "sort": ["-minutes"] },
      { "limit": 10 }
    ]
  }
}

SQL equivalent

SELECT visitorId,
       SUM(numMinutes) AS minutes
FROM events
WHERE day >= NOW() - INTERVAL '30 days'  -- first=now(), count=-30
  AND visitorId NOT LIKE '\_PENDO%'        -- identified
GROUP BY visitorId
ORDER BY minutes DESC                      -- "-minutes"
LIMIT 10;

Read it as: requestId = a query name/label · pipeline = the query body · timeSeries rides along with the source and is your mandatory date filter for event sources.

Sources = tables

Sources are what you FROM. There's no fixed SQL table to map each one to — instead, here's the catalogue from the internal Aggregation Sources wiki, grouped by kind. Entity sources are time-insensitive; event sources require a timeSeries.

Entities (one row per object, current metadata)

SourceWhat a row is
visitorsOne row per visitor in the subscription, for all time, with current metadata. By default returns both identified and anonymous visitors — use the identified operator to filter.
accountsOne row per account, with current metadata.
doNotProcessVisitors / doNotProcessAccountsVariants of visitors/accounts that return only records flagged doNotProcess (part of Pendo's GDPR delete flow).
pagesOne row per tagged Page — an individual screen of the app.
featuresOne row per Feature — an interactable element (buttons, toggles, etc.).
trackTypesOne row per Track Type — deeper, behind-the-scenes tracked events (e.g. time-to-load). Pages/features/trackTypes all derive from the generic “countable” type.
guides / appsOne row per guide (in-app message) / per app in the subscription.

Pre-aggregated event sources (“baserow”) — need a timeSeries

SourceWhat a row is
eventsOverall activity, bucketed per visitor/account over time and baked down into numEvents + numMinutes. A summary row, not a raw event. Best for activity-over-time analytics.
pageEventsSame shape as events, but activity on a particular Page (or all activity broken down by Page). Pass {"pageId": …} to scope.
featureEventsSame as pageEvents, but for a Feature.
trackEventsSame as above, for Track Events. Pre-aggregated — multiple track events may roll into a single row. For individual track events, use singleEvents.

Per-event sources (one row per raw event) — heavy; need a timeSeries

SourceWhat a row is
singleEventsOne row per individual event, lightly processed for readability. This is the per-event source actually used in the app. Massive — use small date ranges and a limit; even a couple of hours can be a lot of data. Not documented to customers; throttled on APIv1.
rawEventsThe most unfiltered events received — debugging only, not used in the app (large, slow, not analytics-friendly). Same granularity as singleEvents but worse-formatted. Prefer singleEvents. Not documented to customers; heavily throttled and may be blocked — don't suggest it to customers.
guideEventssingleEvents pre-filtered to guide-type events (guideSeen/guideAdvanced/guideDismissed). Treated as lighter-weight than singleEvents.
pollEventssingleEvents pre-filtered to poll-type events. One row per poll response.

Summary & utility sources

SourceWhat a row is
timespanWhich days a visitor (in an account) did something in the app. Maps ~1:1 to the events/pageEvents/featureEvents/trackEvents sources.
guidesSeen / pollsSeenVisitors that last saw a given guide/poll within the timeSeries. Require a timeSeries.
guidesSeenEver / pollsSeenEverVisitors that have ever seen a given guide/poll. Time-insensitive — no timeSeries needed.
constEmits a supplied list of literal JSON rows as-is. Great for testing pipelines without hitting real data.
entityTag(visitorTags/accountTags) Used mainly to convert CSV uploads into segments.
recordingMetadataContextual info about Session Replay recordings.
churnInsightsML-generated insights over pages/features (partitioned by eligible vs. filtered results).
itemSeen / gcsitemSeen: reads item-seen files directly (avoids opening the visitor journal). gcs: used by the front-end to download path reports as CSV.
SQL gut-check: the events family is pre-aggregated (a daily/hourly “baserow” roll-up carrying numEvents/numMinutes), so it behaves like a summary table — you SUM those counts rather than counting raw rows. When you genuinely need individual interactions, reach for singleEvents (per-event, lightly processed — what the app itself uses), or, for debugging only, rawEvents (same granularity, unprocessed, slow, not for customer use). Rule of thumb: events for trends over time, singleEvents for event-level detail, rawEvents almost never.

Operators = clauses

Each pipeline step is { "operatorName": params }. Here's each operator mapped to its SQL counterpart.

filter

WHERE / HAVING

Keep rows where an expression is true. After a group, it acts like HAVING.

Pendo

{ "filter": "numMinutes > 5 && country == \"US\"" }

SQL

WHERE numMinutes > 5 AND country = 'US'

identified

WHERE … NOT LIKE anon

A special-case filter: drops anonymous visitors. Pendo gives anonymous visitors a _PENDO_T_* id; this operator filters on that prefix. Invert with "!visitorId" to get only anonymous visitors.

Pendo

{ "identified": "visitorId" }

SQL

WHERE visitorId NOT LIKE '\_PENDO\_T\_%'  -- not anonymous

group

GROUP BY

Group by one or more fields and aggregate. group = your GROUP BY columns, fields = the aggregates. Output rows keep both. With no fields, it just returns the unique combinations (like SELECT DISTINCT).

Pendo

{ "group": {
    "group": ["visitorId", "accountId"],
    "fields": {
      "totalTime": { "sum": "numMinutes" },
      "num":       { "count": null }
    }
} }

SQL

SELECT visitorId, accountId,
       SUM(numMinutes) AS totalTime,
       COUNT(*)        AS num
FROM ...
GROUP BY visitorId, accountId;

Performance tip: putting a limit immediately after group is an optimization — rows come back complete (not partial), but ordering isn't guaranteed.

reduce

aggregate, no GROUP BY

Collapse all rows into a single row of aggregates — same aggregator syntax as group.fields, but no grouping key. Like a bare SELECT COUNT(*), SUM(…) over the whole set. Use this (with a count aggregator) when you need unique counts.

Pendo

{ "reduce": {
    "eventCount":   { "count": null },
    "totalMinutes": { "sum": "numMinutes" }
} }

SQL

SELECT COUNT(*)        AS eventCount,
       SUM(numMinutes) AS totalMinutes
FROM ...;   -- collapses to one row

count

COUNT(*)

Counts input rows, emits a single { "count": N } row. Takes only null. For unique counts, use reduce/group with a count aggregator instead.

Pendo

{ "count": null }

SQL

SELECT COUNT(*) FROM ...;

select

SELECT (projection)

Builds a new row from the listed fields/expressions and discards everything else. An explicit column list (and you can rename).

Pendo

{ "select": {
    "visitorId":      "visitorId",
    "numberOfEvents": "numEvents"
} }

SQL

SELECT visitorId,
       numEvents AS numberOfEvents
FROM ...;  -- only these two columns survive

Want a SELECT *? Just omit select entirely — with no projection step, rows flow through the pipeline carrying all of their fields.

eval

SELECT *, expr AS new

Adds or replaces fields via expressions while keeping the rest. (Contrast with select, which drops the rest.)

Pendo

{ "eval": {
    "eventsPerMinute": "numEvents / numMinutes"
} }

SQL

SELECT *,
       numEvents / numMinutes AS eventsPerMinute
FROM ...;

Heads-up: within a single eval the order the expressions run is undefined. If one new field depends on another, split them into two eval steps.

set

SELECT *, const AS new

Like eval but assigns constant values rather than expressions.

Pendo

{ "set": { "homeAddress": "unknown" } }

SQL

SELECT *, 'unknown' AS homeAddress FROM ...;

switch

CASE WHEN

Bucket a field into a new field by range/condition. Rows that match no case are dropped (unlike SQL CASE, which yields NULL).

Pendo

{ "switch": { "tier": { "minutes": [
    { "value": "low",  "<": 10 },
    { "value": "mid",  ">=": 10, "<": 30 },
    { "value": "high", ">=": 30 }
] } } }

SQL

SELECT *,
  CASE WHEN minutes < 10 THEN 'low'
       WHEN minutes < 30 THEN 'mid'
       ELSE 'high' END AS tier
FROM ...;

sort

ORDER BY

Order by a field list (priority order). Prefix a field with - for descending.

Pendo

{ "sort": ["-minutes", "visitorId"] }

SQL

ORDER BY minutes DESC, visitorId ASC

limit

LIMIT

Keep the first n rows. (sample is the cousin that keeps a random n instead.) Best practice when exploring: limit to 1 just to see the schema.

Pendo

{ "limit": 25 }

SQL

LIMIT 25;

join

JOIN / merge on key

Merges rows that share a key into one row.

Field conflicts: if two rows being merged both set the same field, the row encountered later in the join wins (last-write-wins). So order the branches feeding the join with that in mind.

Do you need width up front? No — it's optional. width tells join how many rows with the same key make up a complete result; once that many arrive, the merged row is emitted downstream early (a perf win). If more rows with that key appear later, they start a fresh merge. Any key that ends with fewer than width rows is still flushed once all input has been seen. So you can omit it and join still works — setting it just lets results stream out sooner. Most commonly used right after fork/spawn.

Pendo

{ "join": { "fields": ["visitorId"], "width": 2 } }

SQL

-- merge the branch rows sharing visitorId into one,
-- later branch wins on any shared column
SELECT visitorId, ...
FROM branch_a
FULL JOIN branch_b USING (visitorId);

bulkExpand

JOIN, packed into a structure

Enriches each row with metadata from the visitor/account journals. It looks up the record and nests the whole thing under a named sub-field (here info) — it doesn't flatten the columns in. Supports visitorId and accountId only. So in SQL terms it's a left join where the joined row is packed into one structure/JSON column.

Pendo

{ "bulkExpand": { "info": { "visitor": "visitorId" } } }

SQL

-- "info" becomes a nested structure holding the
-- whole visitor record, alongside the event fields
SELECT e.*, to_json(v) AS info
FROM events e
LEFT JOIN visitors v ON v.id = e.visitorId;

Performance tip: limit/filter/segment down to the visitors you care about before bulkExpand, so you're not expanding every visitor in the journal and discarding them later.

segment

WHERE IN (subquery)

Passes only rows whose visitorId belongs to a saved segment.

Pendo

{ "segment": { "id": "seg-abc123" } }

SQL

WHERE visitorId IN (
  SELECT visitorId FROM segment_members
  WHERE segment_id = 'seg-abc123'
);

unwind

UNNEST / explode

Expands a list field into one row per element (optionally adds an index). One-to-many fan-out.

Pendo

{ "unwind": { "field": "items", "index": "itemIndex" } }

SQL

SELECT t.*, item, idx
FROM t
CROSS JOIN UNNEST(t.items) WITH ORDINALITY AS u(item, idx);

Empty list → no rows, unless {"keepEmpty": true} (≈ LEFT JOIN UNNEST).

fork

UNION ALL of branches

Sends the incoming rows into multiple sub-pipelines (each gets all the rows), does different work in each, then funnels every branch's output back into the parent pipeline. Empty branches aren't allowed — use a single cat if you need a pass-through branch. Often paired with join.

Pendo (real wiki example)

{ "fork": [
  [ { "group": {
        "group": ["visitorId"],
        "fields": [ { "time": { "sum": "numMinutes" } } ]
  } } ],
  [ { "group": {
        "group": ["accountId"],
        "fields": [ { "time": { "sum": "numMinutes" } } ]
  } } ]
] }

SQL

-- total minutes per visitor, AND per account,
-- in one combined stream
SELECT visitorId AS id, SUM(numMinutes) AS time
FROM events GROUP BY visitorId
UNION ALL
SELECT accountId AS id, SUM(numMinutes) AS time
FROM events GROUP BY accountId;

Pendo result (example shape)

{ "results": [
  { "visitorId": "user-1", "time": 42 },
  { "visitorId": "user-2", "time": 17 },
  { "accountId": "Acme",   "time": 59 },
  { "accountId": "Globex", "time": 23 }
] }

spawn

UNION ALL of different sources

Like fork, but each branch supplies its own source — this is how you pull from several sources into one stream. Then you usually join the branches back together on a key (the classic “combine two poll responses per visitor” pattern below).

Constraint: sources used in spawn cannot have an “iterative” timeSeries (i.e. one that expands into multiple periods). Use all-time / single-period sources here.

Pendo (real wiki example)

{ "spawn": [
  [ { "source": { "pollsSeenEver":
        { "guideId": "G", "pollId": "p1" } } },
    { "identified": "visitorId" },
    { "select": { "visitorId": "visitorId",
                  "quantResponse": "response" } } ],
  [ { "source": { "pollsSeenEver":
        { "guideId": "G", "pollId": "p2" } } },
    { "identified": "visitorId" },
    { "select": { "visitorId": "visitorId",
                  "qualResponse": "response" } } ]
] }
// usually followed by:
{ "join": { "fields": ["visitorId"], "width": 2 } }

SQL

-- one row per visitor with both poll answers
SELECT a.visitorId,
       a.response AS quantResponse,
       b.response AS qualResponse
FROM pollsSeenEver_p1 a
FULL JOIN pollsSeenEver_p2 b USING (visitorId);
-- (spawn = the two branches; join = the merge)

Pendo result — spawn merges both sources into one stream (example shape)

{ "results": [
  { "visitorId": "user-1", "quantResponse": 9 },
  { "visitorId": "user-2", "quantResponse": 7 },
  { "visitorId": "user-1", "qualResponse": "Love it" },
  { "visitorId": "user-2", "qualResponse": "Could be faster" }
] }

After the join on visitorId, each visitor's two rows merge into one combined row.

unmarshal

JSON_PARSE

Parses a JSON string in field input into addressable sub-fields under output. In practice you'll see it almost only with rawEvents — only a few sources carry an unparsed JSON blob, and that's the main one. It's typically followed by unwind to split each embedded event into its own row.

Pendo

{ "unmarshal": { "destField": "rawJson" } }

SQL

SELECT JSON_PARSE(rawJson) AS destField, ...
FROM raw_events;

useragent

no SQL equivalent

Parses a user-agent string in field input into a structured object under output: name, version, os, type, deviceType, renderVersion. There's no native SQL counterpart — it's a built-in parser (you'd reach for a UDF in SQL).

Pendo

{ "useragent": { "parsedUA": "userAgent" } }

SQL

-- no built-in equivalent; would require a UDF, e.g.
-- SELECT parse_user_agent(userAgent) AS parsedUA ...

cat

no-op (pass-through)

Does nothing — passes rows straight through. The wiki literally says “you probably never need to use it.” The one real use is as a placeholder pass-through branch inside a fork (where empty branches aren't allowed).

Pendo

{ "cat": null }

SQL

-- no equivalent; it's a pass-through (rows unchanged)

These are the functions you put in fields / reduce. Form is { "outName": { "aggName": "inField-or-expr" } } — the input can be an expression, e.g. { "sum": "time - 100" }.

Expression functions → SQL functions

Expressions (used in filter, eval, select, timeSeries.first) follow C-style syntax. Operators: == != && || < > <= >= + - / * % !. All numbers are treated as floats. (The full function list lives in aggregation/expr/funcs.go.)

Worked end-to-end examples

Full pipelines translated to full SQL — read top-to-bottom on both sides.

1 · Minutes per identified visitor, last 30 days, top 10

Pendo

{ "request": { "pipeline": [
  { "source": { "events": null },
    "timeSeries": { "period": "dayRange",
                    "first": "now()",
                    "count": -30 } },
  { "identified": "visitorId" },
  { "group": { "group": ["visitorId"],
      "fields": [ { "minutes": { "sum": "numMinutes" } } ] } },
  { "sort": ["-minutes"] },
  { "limit": 10 }
] } }

SQL

SELECT visitorId, SUM(numMinutes) AS minutes
FROM events
WHERE day >= NOW() - INTERVAL '30 days'
  AND visitorId NOT LIKE '\_PENDO%'
GROUP BY visitorId
ORDER BY minutes DESC
LIMIT 10;

first: "now()" with count: -30 = the 30 day-periods ending now (negative count walks backward).

2 · Total events & unique visitors (single summary row)

Pendo

{ "request": { "pipeline": [
  { "source": { "events": null },
    "timeSeries": { "period": "dayRange",
                    "first": 1404745200000, "count": 30 } },
  { "reduce": {
      "totalEvents":    { "sum": "numEvents" },
      "uniqueVisitors": { "count": "visitorId" }
  } }
] } }

SQL

SELECT SUM(numEvents)            AS totalEvents,
       COUNT(DISTINCT visitorId) AS uniqueVisitors
FROM events
WHERE day >= '2014-07-07'
  AND day <  '2014-08-06';

3 · Bucket visitors into engagement tiers

Pendo

{ "request": { "pipeline": [
  { "source": { "events": null },
    "timeSeries": { "period": "dayRange",
                    "first": 1404745200000, "count": 30 } },
  { "group": { "group": ["visitorId"],
      "fields": [ { "minutes": { "sum": "numMinutes" } } ] } },
  { "switch": { "tier": { "minutes": [
      { "value": "low",   "<": 10 },
      { "value": "mid",   ">=": 10, "<": 60 },
      { "value": "power", ">=": 60 }
  ] } } },
  { "group": { "group": ["tier"],
      "fields": [ { "visitors": { "count": null } } ] } }
] } }

SQL

WITH per_visitor AS (
  SELECT visitorId, SUM(numMinutes) AS minutes
  FROM events
  WHERE day >= '2014-07-07' AND day < '2014-08-06'
  GROUP BY visitorId
)
SELECT
  CASE WHEN minutes < 10 THEN 'low'
       WHEN minutes < 60 THEN 'mid'
       ELSE 'power' END AS tier,
  COUNT(*) AS visitors
FROM per_visitor
GROUP BY tier;

Note how the two-stage Pendo pipeline (group → switch → group) reads exactly like a CTE feeding an outer aggregate in SQL.

Final clarifications

Order is execution order. No optimizer reorders your steps. Filter early to keep row counts (and runtime) down — same instinct as a good WHERE, but here it's literal.
select drops, eval keeps — and no select = SELECT *. select is an explicit projection (everything else gone); eval/set add columns alongside existing ones; omitting select entirely passes all fields through.
switch drops non-matches. Unlike SQL CASE (which returns NULL), a row matching no case is removed. Add a catch-all condition to keep everything.
Time is mandatory & in epoch (ms). Event sources require a timeSeries. first is milliseconds since epoch, stating the start of the time range; count is the number of periods (negative walks backward from first). Entity sources (visitors, pages…) don't take one.
Pick the right events source. events/pageEvents/featureEvents/trackEvents are pre-aggregated roll-ups (numEvents/numMinutes) — great for trends, but you SUM counts rather than counting raw rows. For event-level detail use singleEvents (what the app uses); rawEvents is debugging-only and best avoided.
count with a field = DISTINCT. Inside group/reduce, { "count": null } is COUNT(*); { "count": "visitorId" } is COUNT(DISTINCT visitorId). Easy to mix up.
